# Technical Deployment Walkthrough

## Core Components
* **Code.gs:** The backend logic for parsing dictionaries, injecting Google Form items, building HTML emails, handling triggers, running strict authentication checks for alias emails, and interfacing with the cron lifecycle properties.
* **sidebar.html:** The frontend UI controller that manages state, dynamic dropdowns (like the Minors toggle), and constructs the payload passed to the backend for form generation.
* **ManageEventsSidebar.html [NEW in V2.7]:** The frontend UI controller for the Active Events Management tool. It interfaces directly with the backend to read and write active event lifecycle configurations (registration dates, waitlist limits, contact emails) into the master script properties.

## Process Flow

### 1. Initialization and Dictionary Sync
When `Setup Initial Configuration` is run, the script writes a hardcoded Master Dictionary and Template list directly into the Google Sheet (`Field Dictionary` and `Templates` tabs). The `sidebar.html` fetches this live data using `google.script.run` to render the UI checkboxes.

### 2. Frontend Dynamic Logic (sidebar.html)
The frontend listens for template changes. If SSC, YASC, CYSC, or SMC is selected, it unveils conditional UI components (Region, Season, Year, Class). It dynamically constructs the title string in real-time.
**Minors Pre-Configuration & Field Ordering [V2.8]:** The frontend detects youth templates (like SSC, NYTS) and toggles `includesMinors` to "Yes". On the backend, `Age` is validated (1-99) and positioned before class/grade, and `Parent/Guardian` is automatically placed below `Age` with N/A instructions.
**Date Simplification & Defaults (V2.7/V2.8):** The Event Start and Event End date inputs capture clean dates with optional time indicators, while Registration Windows enforce default bounds of 12:01 AM start and 11:59 PM close.

### 3. Backend Generation (Code.gs)
The `generateForm` function takes the payload and programmatically creates a Google Form and a linked Google Sheet (the "Response Sheet").
**Alias Authentication:** Before creating the form, the script validates that the `Session.getActiveUser().getEmail()` matches either the specified `contactEmail` or is an authorized alias via `GmailApp.getAliases()`. This strict check ensures background triggers successfully send automated emails from the correct mailbox.
**Minors Injection:** If `includesMinors` is true, the script dynamically builds a minor disclaimer into the form description and automatically places the *Minor's Email (at least 13 years of age)* field early in the form. Non-minor events proactively purge parent/guardian fields.
**Travel Branching (V2.8):** Form sections are wired to route participants to dedicated flight or train/bus arrival/departure sections dynamically based on their multiple-choice selections.
**Class Filtering:** Inside `addFieldToForm`, the script intercepts the "Class to attend" field. It cross-references the `eventDetails.classes` array from the payload and automatically strips unselected classes using standard array `.filter()` logic.
**Sheet Formatting:** It generates tabs in the Response Sheet: Airport Summary, Participants, Pickup, Drop-Off, and Logistics, styling their headers programmatically and locking the top rows.

### 4. Active Event Management & Live Sync (V2.7 & V2.8 Integration)
Forms generated by the system register their specific lifecycle metadata (registration open/close times, max attendees) into `PropertiesService`. 
When event coordinators open the **Manage Active Events** sidebar, `Code.gs` retrieves these forms using `getMonitoredEvents()`. Changes made in the UI are pushed back to the backend via `updateMonitoredEvent()`, modifying the master properties, automatically synchronizing updated contact emails into the response sheet's `Settings` tab (V2.8), and explicitly re-triggering the form lifecycle cron job (`masterFormLifecycleCron`) to ensure changes (like opening, closing, or displaying custom closed messages) take effect in real-time.

### 5. Event Triggers and "The Mothership" Architecture
`generateForm` binds an Installable Trigger (`ScriptApp.newTrigger`) pointing back to `masterRespondToRegistration` in the Master Apps Script project, but configures it to listen to the child Response Sheet. Auto-archiving selectively caps form triggers while strictly preserving system cron triggers (V2.8).
This "Mothership" architecture ensures that all generated forms instantly benefit from future script updates.

### 6. Automated Logistics (masterRespondToRegistration)
When a form is submitted, the master script runs:
*   **Dynamic Headers:** It searches the live spreadsheet row to bypass Google Forms edit omission bugs, handling translated column headers gracefully.
*   **Flight & Train/Bus Sync (V2.8):** If flight or train/bus travel is detected, details are statically extracted and appended or updated on the Pickup and Drop-Off sheets. Edits apply warning highlighting (yellow), and cancellations apply strike-throughs (red).
*   **Safe Sorting:** Immediately after updating, it executes `.sort()` on the entire data range. Because this is static data sorting, manually typed driver names stay perfectly aligned with the passenger rows.
*   **Email Routing:** It fetches the form using `FormApp.openByUrl()`, matches the participant's email (excluding minor email entries in V2.8), extracts their `EditResponseUrl`, and injects a formatted HTML button into the custom confirmation email.
